## What happened

Slurm 8454498 ran November 17, 14:33:36–22:39:03 Eastern, and failed after
8h05m27s (exit 1). Collection completed in about 5h38m, bank construction took
about eight minutes, and the context-only fit/evaluation took about 1h47m.
The whole-draft fit completed its first epoch and development evaluation, then
stopped while committing checkpoints. Its latest valid checkpoint contains all
6,226 first-epoch updates, so no optimizer updates need to be repeated.

The failure was reproduced on November 19: creating a 14-byte file in the run
directory raised `OSError: [Errno 28] No space left on device`. The shared filesystem
reported roughly 30 TB free and no inode shortage; `quota -vs` returned no usable
quota information. This establishes exhausted writable home allocation, consistent
with a directory/account quota, rather than exhaustion of the shared filesystem.
The failed job could not even write its error status or traceback. The exact
quota setting was not obtained. Slurm did not report a time limit or GPU OOM.

## Dataset actually used

All 50,000 training and 1,024 validation prompts were processed. Collection and
independent bank construction checked 3,235,678 emitted target positions.

- Optimization: **199,205 blocks from 49,953 prompts**; 47 prompts had no eligible
  complete block. Of these blocks, 197,032 are repairable and 2,173 preservation.
- Development: 2,048 blocks from 512 excluded prompts.
- Final test: 2,040 blocks from all 512 reserved prompts; some short continuations
  provide fewer than four complete blocks. Test includes 1,682 repairable,
  324 wrong-first and 34 preservation blocks.
- The bank hash and SQLite integrity pass. Independent recount found no exact
  normalized family overlap among optimization, development and test.

This is the full prompt inventory with up to four blocks per prompt, not training
on every token of the historical saved responses.

## Completed context-only result

The 40,750,336-parameter context/seed variant completed three epochs and 18,678
updates. Development selection chose epoch three. A correct-prefix measurement
counts consecutive matching proposal tokens after the fixed target anchor,
with a maximum of 15.

| Reserved-test measurement | Result |
|---|---:|
| DFlash original mean correct prefix | 3.5422 |
| Editor replacement mean correct prefix | 2.0176 |
| Replacement change | −43.0% |
| Hypothetical best of original/edited prefixes | 3.9843 |
| Improved / worsened / unchanged blocks | 275 / 955 / 810 |
| Improved / worsened / unchanged prompt means | 73 / 407 / 32 |
| Initially perfect proposals damaged | 34 / 34 |
| Exact generated editable suffixes | 4 / 2,040 |
| Editable token accuracy | 3,644 / 28,560 = 12.76% |
| Isolated cached FP32 editor latency | 19.10 ms |

Both sources worsened: UltraChat 2.5502→1.5768; GSM8K 4.5264→2.4551.
Wrong-first examples remain at zero because the editor preserves that token.
The 34 perfect proposals were all damaged by this context-only variant.

Training learned something: mean CE over the first 100 update batches was 10.2773,
versus 2.5114 over the final 100. Development CE improved 3.4586→3.0795→3.0171,
and edited prefix improved 1.7251→1.9268→2.0752. Nevertheless, final-test
replacement remains substantially worse than the original proposal.
Batch training losses are different shuffled samples, not a fixed training-set
evaluation or proof of whole-corpus memorization.

The best-of-two prefix is an offline coverage calculation. It assumes retaining
the original proposal and selecting the better verified branch; it does not
include that branch-verification cost and is not a deployed speedup. The 19.10 ms
measurement excludes the target and drafter. The current context-only variant
does not justify an unconditional replacement policy.

The whole-draft variant's first-epoch development result was 3.2100 against a
3.5776 original baseline (234 improvements, 412 regressions). This is partial
development evidence, not its final selected-checkpoint test result. Wait for
the authorized fit and audit before drawing the full comparison or changing
the architecture/objective.

## Tests and independent evidence

**34 CPU tests passed in 4.03 seconds** on November 19: 30 existing checks and four
new checks. The new save test injects an actual partial temporary-file write and
ENOSPC, then proves that the last committed checkpoint survives and recovery can
write/load a new checkpoint. Three result-audit tests reject wrong summaries,
wrong per-row counts, changed labels/seed tokens, changed identities and missing
predictions. The unchanged checkpoint writer already provides atomic replacement;
this incident required storage recovery rather than changing training arithmetic.

The independent context recount checks every saved prediction against the
immutable bank, recomputes all token/prefix/repair/preservation metrics, verifies
all three development reports and checkpoint selection, and checks both
checkpoint hashes. It uses no training/evaluation helper. CE cannot be recovered
from argmax tokens and is explicitly not independently recomputed.
The original GPU runner also passed selected-checkpoint reload and cached/full
generation equivalence on 64 fixed context-mode test blocks.
